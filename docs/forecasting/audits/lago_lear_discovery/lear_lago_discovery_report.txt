1. Executive summary

- This repository already has a mature hourly DA forecasting pipeline with fixed split semantics, daily rolling origins, `D..D+4` horizon handling, shared evaluation, and run artifact contracts.
- Hourly NL DA cleaned data currently covers `2021-12-31 23:00:00+00:00` through `2025-09-30 21:00:00+00:00` at hourly resolution (with interpolation/missing flags present).
- Exogenous cleaned families exist for load and generation aggregates, plus generation-by-PSR actuals/capacity. Separate NL wind-forecast and solar-forecast families were not found.
- Import/cleaning scripts can be extended backward by year, but extension is not range-safe by default (same-year reruns overwrite raw files with deterministic filenames).
- Current strong comparison baselines exist (FS2 and FS3 runs), but “best” depends on objective: LEAR is stronger on some D-only views, XGBoost stronger on most full-horizon views.
- No implementation was performed; this is read-only discovery.

6. Current split and horizon logic

F) Split logic
- Official hourly split:
  - train: `2022-01-01` to `2023-09-30`
  - validation: `2023-10-01` to `2024-09-30`
  - test: `2024-10-01` to `2025-09-30`
- Defined in: `hourly_da/core/config.py::HourlyDAPipelineConfig`
- Hardcoded vs configurable:
  - hardcoded defaults in dataclass
  - configurable only by constructing a different config object in scripts/code (no separate split YAML/JSON mechanism found for hourly)
- Safe representation for a new six-year Lago split:
  - use a separate run script/config object with custom `train_*`, `validation_*`, `test_*` dates and a unique run label/output folder.
  - do not overwrite official cleaned files or canonical runs.
- Separate experiment mechanism:
  - run isolation exists via timestamped run folders (`core/storage.py::create_run_directory`), not via a dedicated split registry.

G) Forecast origin/horizon logic
- Origin representation:
  - `forecast_origin_local`, `forecast_origin_utc` in `core/schedule.py`
  - daily origins generated by `generate_forecast_origins()`
- D-1 08:00 encoding:
  - yes (`forecast_origin_local_hour=8`, `forecast_origin_local_minute=0`)
  - `origin_local_day = delivery_start_local_date - 1 day`
- Delivery timestamp representation:
  - `target_timestamp_utc`, `target_delivery_local_date`, `target_hour_local`
- Horizon representation:
  - `lead_day` (`0..4`), `lead_day_label` (`D`, `D+1`, ...), `horizon_index`
- D-only vs D..D+4:
  - reporting levels in `core/reporting.py`: `d_only`, `guidance_only`, `stitched_all_horizon`
- Compatibility schema (predictions):
  - `run_id, model, model_family, fs_level, dataset_split, forecast_origin_utc, target_timestamp_utc, target_delivery_local_date, target_hour_local, target_known_at_utc, lead_day, lead_day_label, horizon_index, y_true, y_pred, is_observed_target, fit_time_sec, predict_time_sec, fit_time_warning*`

11. Blockers, assumptions, and risks

M) Hard blockers
- No separate NL wind forecast / solar forecast family found in current importer/cleaner stack.
- Current hourly cleaned NL DA file stops at 2025-09-30 21:00 UTC; new target horizon ending 2025-10-01 may require refresh/extension decisions.

Soft blockers
- Import and cleaning defaults use `data/00_Raw` while existing tree is `data/00_raw` (Windows masks this; cross-platform risk).
- Some FS3 candidate run labels and contained model names are inconsistent (pruned runs still contain model names with `...promoted`), which can confuse comparison automation.

Leakage/timing risks
- known-at policy is internally consistent but based on simplified publication assumptions (`day_ahead_local_08`, `week_ahead_local_08`), not an externally audited publication-timing model.
- Using forecast families without strict publication metadata would risk leakage; current cleaned exogenous files include known-at columns, which should be preserved.

Timezone/DST risks
- UTC storage is strong; risk is primarily at local-day boundary logic.
- DA cleaning default timezone is `Europe/Brussels`; NL business timezone is `Europe/Amsterdam` (currently same DST rules, but keep explicit alignment).

API extension risks
- Older historical availability may be incomplete.
- Year reruns can overwrite same-year raw files.
- Pagination caps/timeouts can truncate imports if not monitored.

Comparison risks
- Comparing new benchmark vs existing FS3 outputs over mismatched periods/splits will produce misleading conclusions.
- rMAE denominators must be aligned to comparable benchmark contexts.
